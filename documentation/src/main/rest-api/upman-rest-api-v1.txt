The Unity UpMan REST API may be exposed (or disabled) as a regular Unity endpoint. See the
link:manual.html#endp-rest-upman[main Unity documentation] for endpoints configuration details.

All paths must be naturally prefixed with the server's base URL, endpoint deployment's path
(as configured) and API version (currently there is only one). Example query path can be similar to:

   https://unity.example.com/rest-upman/v1/projects/PROJECT-ID

== Generated API reference

Use the link:upman-openapi-v1.html[generated UpMan API reference] for operations,
parameters, request/response schemas and examples. The
link:upman-openapi-v1.yaml[OpenAPI YAML] can be imported into API clients.
The API version is independent of the Unity product release version.

The live +openapi.yaml+ and +openapi.json+ documents are available below the deployed
endpoint path and use the endpoint's existing authentication. The published reference
uses a relative server URL; configure the deployment URL in your API client.

== Authorization

The API supports two authentication methods. All project access is limited to the endpoint's configured
projects root.

=== Direct authentication

* Required permission: the authenticated Unity entity must have +sys:ProjectManagementRESTAPIRole+
set to +manager+ in the endpoint's configured authorization group.
* This role permits creating projects and managing every project under the configured projects root.
* The authenticated entity does not need membership or a project-local management role in those projects.

=== OAuth bearer token

Send the access token in the +Authorization: Bearer ACCESS_TOKEN+ header. A valid token authenticates
the API request.

UpMan authorizes API operations using only the token's granted scopes. It does not check the REST API role,
project membership or project-local management roles of either the client entity or the resource owner entity.

The scopes grant the following permissions:

* +sys:upman-api+: permits creating projects and managing every project under the configured projects root.
* +sys:upman-api:PROJECT-ID+: permits managing exactly the specified project. Project listings show only
projects matched by the token's scopes. This scope does not permit creating projects.

Project IDs are paths relative to the configured projects root. For example:

* +sys:upman-api:A+ permits managing project +A+, including removing its subprojects and changing their
delegation configuration through +A+.
* To access +A/child+ as a project in its own right, the token needs +sys:upman-api:A/child+ or the global
+sys:upman-api+ scope. The scope for +A+ alone does not grant this access.

A token without a matching UpMan scope is denied access. The authorization server's client and scope
configuration controls which clients can obtain tokens with these permissions, even when the resource
owner has no management role in the affected projects.

An already issued bearer token remains usable while the token itself is valid, even if the OAuth client's
password is subsequently marked outdated.

=== Rules for both methods

* Authentication must succeed using the selected method. Direct password authentication with an outdated
password is rejected. With bearer authentication, the selected credential is the access token; the client's
password being outdated does not by itself reject an otherwise valid token.
* The REST API manager role or a matching OAuth scope permits granting +projectsAdmin+ to project members,
deleting subprojects and changing subproject delegation settings. The caller does not need a separate
+projectsAdmin+ role to perform these operations.
* These operations require delegation to be enabled on the project. Deleting a subproject or changing its
delegation settings also requires +enableSubprojects+ to be enabled on the parent project. The REST API
role and OAuth scopes do not override these project settings.

== Project and group paths

Projects must exist under the configured root and have delegation enabled.
Use the +urlId+ returned in project listings as the project identifier in request paths.
Project-specific OAuth scopes use +projectId+, the relative project path, instead of +urlId+.
The create response contains +id+; retrieve the listing to obtain the URL identifier.
It encodes a nested project into one URL segment: +a/b+ has URL ID +a%2Fb+.
Names containing a literal percent sign use an opaque URL ID because the server rejects
percent-encoded percent signs in paths. Always use the listed identifier.

Group paths in JSON and query parameters are relative to the selected project.
An empty path selects the project root. Absolute paths, empty path segments and
traversal segments are rejected. The generated parameter descriptions explain where
omitting a query parameter changes the returned representation.

[[group-visibility]]
=== Visibility prerequisites

A public project or subgroup requires all of its ancestor groups to be public, including groups above the
endpoint's configured projects root. Make the ancestors public first when public visibility is required.
The REST manager role and OAuth scopes do not override this constraint.

A request to make a subgroup public under a private parent returns +409+ with an empty body.
The equivalent project update currently returns +500+ with an empty body instead of +409+; this is a known
defect tracked in https://unity-idm.atlassian.net/browse/UY-1626[UY-1626]. These responses currently do not
identify the conflicting parent, so check the ancestor groups' visibility when diagnosing the failure.

== Project workflows

Create a project, then attach the forms appropriate to its workflows. Forms can be
provided explicitly or generated from project configuration. Sending invitations
requires both a registration form and a signup enquiry form. Invitations refer to
relative subgroup paths; refresh the invitation list after replacing an invitation
because its code changes.

Member management supports email addresses and stable numeric entity identifiers.
Use numeric identifiers for users without email. Delegated subgroup role changes
follow the project's authorization rules and must leave a project manager in place.

List pending requests to process registrations, signup enquiries and membership
updates. Decisions use the stored request's type and operation. Completed requests
leave the pending listing. Read the form operation descriptions before changing a
form with pending requests: each flag and its persistence consequences is documented
beside the operation.

== Form workflows

[[form-json]]
=== Form JSON and editing

These routes reuse Unity's registration and enquiry form JSON, also exposed through the
link:rest-api-v1.html#_get_registration_forms[Admin REST registration forms] and
link:rest-api-v1.html#_get_enquiry_forms[Admin REST enquiry forms] routes. See the main manual's
link:manual.html#registration[registration forms] and link:manual.html#enquiry[enquiry forms] sections for the form
settings. To obtain a complete JSON definition, generate a project form or configure one in Admin UI, then
retrieve it through REST.

Form property names are case-sensitive and mix conventions. For example, the form's identifier is +Name+,
its displayed name uses +"DisplayedName":{"Map":{"en":"Join project"},"DefaultValue":null}+, and enquiry forms
also have properties such as +type+ and +targetGroups+. Project and subgroup +displayedName+ values instead
use plain language maps such as +{"en":"Project"}+; do not copy that representation into a form.

Edit and PUT the complete retrieved form, preserving its +Name+ and other settings. For example, after
creating the registration form, change only its English displayed name using +jq+:

[source,shell]
----
UPMAN_URL='https://unity.example.com/rest-upman/v1'
UPMAN_TOKEN='ACCESS_TOKEN'
curl --fail-with-body --silent --show-error \
  -H "Authorization: Bearer $UPMAN_TOKEN" \
  "$UPMAN_URL/projects/my-project-id/registrationForm" \
  -o registration-form.json
jq '.DisplayedName.Map.en = "Join my project"' registration-form.json > registration-form-updated.json
curl --fail-with-body --silent --show-error -X PUT \
  -H "Authorization: Bearer $UPMAN_TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @registration-form-updated.json \
  "$UPMAN_URL/projects/my-project-id/registrationForm"
----

Attributes collected in Unity's root group +/+ must be allowed in the UpMan REST endpoint configuration.
This is separate from the endpoint's projects root. For the +name+ attribute used by autogenerated
registration forms, configure:

----
unity.upman.rest.rootGroupAttributes.1=name
----

Use further numbered entries for other permitted root-group attributes. Without the matching entry, even
a GET followed by an unchanged PUT can return +400+ with a message such as
+Attribute registration parameter name is not permited in root group+.

=== Generate a project form

Generate a registration form with an empty JSON request body:

[source,shell]
----
UPMAN_URL='https://unity.example.com/rest-upman/v1'
UPMAN_TOKEN='ACCESS_TOKEN'
curl --fail-with-body --silent --show-error -i -X POST \
  -H "Authorization: Bearer $UPMAN_TOKEN" \
  -H 'Content-Type: application/json' \
  "$UPMAN_URL/projects/my-project-id/registrationForm?autogenerate=true"
----

Use the same headers and empty-body request for +signUpEnquiry+ and +membershipUpdateEnquiry+.
See <<form-json>> for the root-attribute allowlist required when editing generated forms.
